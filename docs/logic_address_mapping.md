# Logic file — Part B: Linking TIN → NPI → address, and specialty (C5)

**Problem (PS):** rates come with an NPI and a TIN but no address or specialty. One TIN can have many addresses and
one NPI can practise at many addresses. About 80% of NPPES addresses are stale, so NPPES alone is not enough.
Running an address tool on NPPES is a baseline, not a solution.

**Our approach in one line:** collect candidate addresses from **independent** sources, **standardize and validate**
them, use the **TIN–NPI structure of the rate file itself** as corroboration, and grade each address
**VERIFIED / PROBABLE / UNVERIFIED** with the evidence written next to it. **Every rule is tested against data
before it is used** (section 3): one rule we planned was rejected because the data contradicted it.

Numbers come from `data/stage5/c5_report.txt` and `data/stage5/c5_audit.txt` (both generated by the run), except the
statewide study in section 3.4, which is labelled as such.

---

## 1. Sources and what each adds

| Source | What it adds | Why it's independent |
|---|---|---|
| **The rate file** (TIN → NPIs) | which NPIs bill under which TIN: the backbone of the link | it's the contract data itself |
| **NPPES API**: primary LOCATION + secondary practice locations | the provider's self-reported practice sites; taxonomy | maintained by the provider |
| **NPPES API**: endpoint affiliation addresses | an address entered separately from the practice location, usually by the EHR/HIE that registered the provider's Direct/FHIR endpoint | same registry, so counted in the **NPPES family** (it can't confirm NPPES on its own); it can surface a site that other sources then confirm |
| **CMS Doctors & Clinicians (DAC)**, refreshed monthly (dataset modified 2026-10-02) | practice addresses from **Medicare enrolment** (PECOS), with the **group name** per address | a different system with its own verification |
| **CMS facility registries**, CMS Provider Data Catalog (https://data.cms.gov/provider-data/), CA rows: hospital `xubh-q36u`, ambulatory surgery `4jcv-atw7`, medical equipment suppliers `ct36-nrcq`, home health `6jpm-sxkc`; **added 2026-10-18:** dialysis `23ew-n7w9` (734 CA), hospice `yc9t-dgbk` (1,913), inpatient rehabilitation `7t8x-u3ir` (83), long-term care hospitals `azum-44iv` (20), nursing homes `4pq5-n9py` (1,165) | official addresses of **organizations**, which DAC doesn't cover. Matched as before: same building + a shared name word | CMS certification/enrolment data |
| **California Department of Public Health (CDPH), Licensed and Certified Healthcare Facility Listing**, data date 2026-10-16: https://data.chhs.ca.gov/dataset/healthcare-facility-locations (CSV: `config.yaml` `sources.cdph_facility_locations_csv`) | the **state licensing address** of hospitals, surgery centres, clinics, home health, dialysis, nursing facilities…, **with the facility's NPI**, so matching is exact (NPI), not by name. 7,372 open facilities carry an NPI; 491 of our NPIs are listed | a state regulator's inspection and licensing record, separate from NPPES (self-reported) and from Medicare enrolment. Also used as the **referee** of the accuracy audit (§3.6) |
| **US Census geocoder** | confirms the address **exists**; returns a standard form, county and coordinates (used by C7 peers) | an authoritative address reference |
| NPPES MAILING address | **not used**: a billing or mail address, not a place where care is given | — |

**Considered, not used (2026-10-18):**
- **CMS Open Payments, Covered Recipient Profile Supplement** (https://download.cms.gov/openpayments/, file PHPRFL_P01232026):
  downloaded and **rejected**. Its README says the profile addresses are *"derived from … NPPES and PECOS"*, the same
  systems as our NPPES and DAC sources, so counting it would let one source confirm itself. The independent addresses
  (reported by manufacturers) are only in the payment-record files (> 1 GB; the Open Payments API that would allow a
  filtered download returned HTTP 403 to us).
- **CMS Provider of Services file, clinical laboratories (CLIA)**: would cover the ~100 unverified labs, but the
  data.cms.gov catalog and dataset pages returned HTTP 403 on 2026-10-18, so it could not be downloaded reproducibly.
- **Medicare Physician & Other Practitioners (claims)**: its provider addresses come from NPPES, so not independent.

Earlier: Health Net's FHIR provider directory (behind a login on Centene's developer portal); Health
Net's public directory JSON (Medi-Cal only, not commercial); HiLabs MCheck/R3 (not available to us; it would replace
the Census step). The NPPES `Parent Organization TIN` field would be a direct TIN source, but NPPES redacts it:
every populated value is `<UNAVAIL>` (checked on the full Oct-2026 NPPES file). So **TIN links come only from the rate file.**

## 2. Linking rules

1. **Candidates per (NPI, TIN):** every NPPES practice location, secondary location and endpoint address of the NPI,
   plus its DAC addresses. TIN-only contracts (NPI "0") borrow the candidates of the other NPIs on the same TIN.
2. **Same place = same building (D5.7).** Every address is standardized with one shared rule set
   (`src/common/address.py`, unit-tested in `tests/test_address.py`), then validated by the Census geocoder. Buildings
   are compared on standardized street + ZIP5; suites are kept for display only. Each rule exists because real NPPES vs
   Medicare pairs disagreed on it:

   | Rule | Example (same building) |
   |---|---|
   | every word abbreviated in the key (CMS abbreviates mid-name, NPPES often doesn't) | `24411 HEALTH CENTER DR` = `24411 HEALTH CTR DR` |
   | a bare token after the street suffix is a suite | `1317 YNEZ PL A` = `1317 YNEZ PL STE A`; `MCHENRY AVE 340` |
   | spaces inside names ignored | `1010 W LA VETA AVE` = `1010 W LAVETA AVE` |
   | house numbers spelled out | `ONE MEDICAL PLAZA DR` = `1 MEDICAL PLZ DR` |
   | facility name on line 1, street on line 2 | `KAISER MEDICAL OFFICES / 4867 SUNSET BLVD` = `4867 SUNSET BLVD` |
   | route numbers are not suites | `PACIFIC COAST HWY 1` stays as is |
   | PO boxes flagged | a PO box is never a practice location |

   Effect versus the earlier 17-word abbreviation list: more matches of every kind (CMS hospital registry 317 → 328,
   DME 236 → 250, Medicare group 1,280 → 1,338, TIN corroboration 388 → 414). In the statewide study (3.4), 1,855 of
   488,062 building keys group more than one spelling, and a 25-key sample showed no false merge (`HWY 111` /
   `HIGHWAY 111`, `LONE TREE` / `LONETREE`, `MC HENRY` / `MCHENRY`). Typos (`WESMINSTER`) are deliberately **not** guessed: a rule that guesses spellings would merge
   different streets.
3. **Evidence for each (NPI, TIN, address):**
   - `n_independent_sources`: how many source **families** agree on the building: NPPES (location, secondary, endpoint),
     CMS enrolment (DAC individual or the organization's own Medicare group), CMS facility registry
   - `tin_corroboration`: **another NPI billing under the same TIN practises at this address** in its own records. This
     is the TIN → address link: a TIN's addresses are where its NPIs practise
   - `dac_name_match`: the DAC group name at this address shares ≥ 50% of its name tokens with the TIN's business name
     in the rate file. It links the address to *this* TIN when the NPI works for several groups
   - `geocoded`: the Census geocoder matched the address (it exists)
   - `nppes_current` (NPPES updated within 24 months): **reported, but not evidence** (section 3.1)
4. **Tiers:**

| Tier | Rule | Meaning |
|---|---|---|
| **VERIFIED** | the address **exists** (D5.10) **and** (2 independent source families agree **or** 1 family + TIN corroboration **or** 1 family + DAC group-name match), not a PO box | confirmed by two separate pieces of evidence |
| **PROBABLE** | the address **exists** **and** one **non-NPPES** source (DAC, the organization's Medicare group, a CMS facility registry, or the CDPH state licence) | an independent system lists it, but nothing else agrees yet |
| **UNVERIFIED** | everything else: NPPES-only addresses, addresses that don't geocode, PO boxes | kept and labelled, never silently dropped |
| NONE | no candidate address at all | reported |

5. **Many addresses (one-to-many, as the PS requires):** a pair keeps **every** VERIFIED and PROBABLE address. Ranking
   inside a pair = tier, then evidence points (DAC +2, registry +2, TIN corroboration +2, NPPES location / secondary /
   endpoint +1 each, name match +1, geocoded +1, in CA +1). `is_best` marks the top one.
6. **Conflicts:**
   - NPPES and DAC disagree → both kept as separate candidates; the one with more evidence ranks first. Neither is deleted.
   - An address outside CA → kept, flagged `in_state = False`; it ranks lower (labs often bill from another state).
   - An NPI under several TINs → linked separately per TIN; the DAC group-name match decides which site belongs to which TIN.

## 3. Evidence behind the rules (`python -m src.stage5_audit` → `data/stage5/c5_audit.txt`)

### 3.1 D5.8 — A recent NPPES update does **not** mean a correct address (rule rejected)
The first version counted an NPPES address as PROBABLE if the NPPES record was updated in the last 24 months. We
tested that on this run's providers: for NPIs with both an NPPES primary address and a Medicare record, how often does
Medicare list the NPI at the same building?

| NPPES last updated | < 1 y | 1–2 y | 2–5 y | 5–10 y | 10 y + |
|---|---|---|---|---|---|
| NPIs | 34 | 30 | 71 | 71 | 125 |
| Medicare confirms the NPPES primary | 64.7% | 63.3% | 70.4% | 66.2% | 72.0% |

Updated within 24 months: **64.1%**; older: **70.0%**. Recent records are no more accurate, slightly less if anything.
The same holds statewide (section 3.4). `last_updated` moves when *any* NPPES field changes (taxonomy, phone, license),
not specifically the address. **Decision:** recency is reported but never raises a tier. Effect: best-address PROBABLE
fell from 538 to 68 pairs; those addresses are honestly UNVERIFIED (NPPES-only).

### 3.2 NPPES-only baseline vs this pipeline
| | NPIs |
|---|---|
| NPIs in the PPO file | 3,734 |
| Baseline (MCheck-style): an NPPES primary address exists | 3,726 |
| … and an independent source confirms it | 1,803 (48.3%) |
| **Pipeline: NPIs with ≥ 1 VERIFIED address** | **1,859 (49.8%)** |
| … verified only at an address that is *not* their NPPES primary | 56 |
| (NPI, TIN) pairs whose best address is not the NPPES primary | 214 |

**Reading:** for 51.7% of NPIs, the NPPES primary address can't be confirmed by any independent source. The pipeline
doesn't hide that behind a confident-looking address: it labels them UNVERIFIED. Where it does better than the baseline
is (a) a confirmed address for 58 NPIs whose NPPES primary is not confirmed, (b) 190 pairs where a better-supported
address outranks the NPPES one, and (c) one-to-many: 189 NPIs and 220 TINs carry more than one confirmed or probable site.

### 3.3 Which source is the odd one out?
Assuming "Medicare is right, NPPES is stale" is itself an assumption. On this run only 14 NPIs have all three of NPPES
primary, Medicare and an endpoint address (most providers here are organizations, which DAC doesn't list), too few to
conclude. The statewide study (3.4) has 28,623.

### 3.4 Supplementary statewide study (Member B; full NPPES file 2026-10-11 and full CMS DAC national file)
Run on all 1.26 M active California NPIs, independent of the PPO network, to test the assumptions at scale:
- **NPPES vs Medicare:** of 156,805 CA clinicians in both, Medicare lists the NPPES primary building for only **45.7%**.
  For **50.8%** it lists no NPPES address at all, and these are real moves, not spelling: 58% are in another city and
  13% in another state.
- **Recency (D5.8) statewide:** Medicare confirms the NPPES primary 45.4% (updated < 1 y), 52.9% (1–3 y), 40.2% (3–5 y),
  45.1% (5–10 y), 43.4% (10 y +). There is no trend, and removing newly enumerated NPIs changes nothing.
- **Odd one out (28,623 NPIs with NPPES primary P, Medicare D, endpoint E):** all agree 24% · **NPPES primary is the
  outlier 23%** · Medicare the outlier 14% · endpoint the outlier 14% · all differ 25%. NPPES is the least reliable
  single source, but Medicare is also wrong in 14%. **That's why tiers reward agreement between sources, not trust
  in any single one.**

### 3.7 D5.10 "The address exists": Census geocoder, or a government record of the same building
**Problem:** VERIFIED required a US Census geocoder match, to prove the address exists. 437 address rows failed it, and
**170 of them already had 2+ independent source families agreeing on the same building.** Examples are Stanford's
300 Pasteur Drive and "12401 Washington Blvd, Whittier" (a hospital). Census address ranges miss large campuses and new
buildings. Retrying with Census's single-address service matched only 1 of 6 test addresses.
**Rule:** an address exists if the Census geocoder matches it, **or** a government record outside NPPES lists that
exact building (standardized street + ZIP5): Medicare enrolment (DAC), a CMS facility certification, or the CDPH state
licence. Each of these validates addresses in its own system. NPPES alone (self-reported) never proves existence.
Column `address_exists_by` = CENSUS_GEOCODER / GOVERNMENT_RECORD.
**Result:** 120 more VERIFIED best addresses. **Tested, not assumed:** in the hold-out audit (§3.6), VERIFIED accuracy
went from 96.7% (396 pairs) to **97.5% (441 pairs)**, so the rescued addresses are right.

### 3.6 D5.9 How accurate is each tier? Hold-out audit against the state licensing record
**Why:** a tier is only useful if it predicts whether the address is right. We measured that against a referee that
the tiers did **not** use. **How:** C5 runs twice. Run 1 builds the mapping **without CDPH**. Then, for every pair whose
NPI the state lists, CDPH referees run 1's addresses: correct = same building (standardized street + ZIP5) or within
250 m of the state's geocoded location. Run 2 adds CDPH as a source and is the output. [regulator: CDPH 2026-10-16]

| Tier (best address of the pair, run 1) | Pairs refereed | Same building as the state licence | Same ZIP |
|---|---|---|---|
| **VERIFIED** | 441 | **97.5%** | 98.2% |
| UNVERIFIED | 50 | **86.0%** | 90.0% |
| PROBABLE | 0 | not measurable | — |

Over **all** candidate addresses, not only the best one: VERIFIED 90.6%, UNVERIFIED 45.5%. Unverified *alternative*
addresses are usually old or secondary sites, which is why only the best one is shown in the rate file.
**What it changes:** every address row carries `expected_accuracy` (VERIFIED 0.975, UNVERIFIED 0.86; blank for PROBABLE),
which the rate file shows as `address_expected_accuracy`. "UNVERIFIED" means "one source only", and for licensed facilities
that one source is still right about 86% of the time. **Limit:** the referee lists licensed facilities (organizations), so the
figures describe organization addresses; individual clinicians are not in the state facility list.
`data/stage5/c5_cdph_audit.parquet` holds every refereed address.

### 3.5 Mistakes caught and fixed (kept here on purpose)
1. **Circular name evidence.** DAC group addresses were *selected* by an exact name match, and the rule then counted that
   same match again as corroboration, producing up to 195 "verified" addresses per pair. Fixed: the name match only
   counts as evidence for individual DAC rows.
2. **Copying a group's sites to every NPI.** Sutter Bay Medical Foundation has 194 Medicare sites; the first version gave
   all 194 to each of the TIN's 23 organization NPIs and counted the copies as TIN corroboration. Fixed: a group's sites
   only **confirm** an address the NPI itself reports, and TIN corroboration counts only NPIs' **own** records.
3. **Recency used as evidence** (3.1): rejected by the data; removed.
4. **Non-reproducible dates.** The recency flag used today's date, so results changed from day to day. It now uses the
   newest NPPES update in the fetched data.

## 4. Specialty (needed for the rate file)
Rules, first match wins, with `specialty_source` recorded:
1. NPI's primary NPPES taxonomy in the HiLabs Taxonomy-Spec Xwalk → `NPPES_PRIMARY`
2. a secondary taxonomy in the Xwalk → `NPPES_SECONDARY`
3. a facility taxonomy in the NUCC-verified facility map (config `specialty.facility_taxonomy_map`, e.g. Ambulatory
   Surgical 261QA1903X → 045; Urgent Care 261QU0200X → 080; Skilled Nursing 314000000X → 046) → `FACILITY_MAP`
4. from the HiLabs codes the NPI is priced on: the specialty whose weighted code list they cover most, **only if it
   beats the runner-up by 1.5×** → `CODE_PROFILE`
5. otherwise `Unmapped (<NUCC description>)` (e.g. "Unmapped (General Acute Care Hospital)"): kept, not dropped.

Why: the HiLabs crosswalk covers individual taxonomies only. Exact coverage on all 3,734 NPIs (full NPPES file): Type 1
96.7%, Type 2 52.5% (61.8% with the facility map). HiLabs has **no radiology, anesthesiology or pathology specialty**,
so those physicians stay Unmapped even though their taxonomies are individual ones.

**Why NPPES alone is not enough (this run):** 2,618 of 3,726 NPPES records (70%) were last updated more than 24 months
before the newest one; but age is not the problem (3.1). The problem is that **2,138 NPPES primary-location rows have no
independent confirmation at all**, and statewide half of all clinicians are listed somewhere else by Medicare (3.4).

**Limits (honest):**
- Individuals not enrolled in Medicare (not in DAC) and organizations outside the four registries can reach VERIFIED
  only through TIN corroboration; otherwise their NPPES address stays UNVERIFIED.
- Hospitals have no HiLabs specialty ("Unmapped (General Acute Care Hospital)", 226 NPIs).
- Building-level matching treats two practices in the same building as the same address; suites are shown but not used for matching.
- The Census geocoder can't match 7% of addresses (PO boxes, new streets); those stay UNVERIFIED rather than being guessed.
- The statewide study (3.4) was run on the bulk NPPES and DAC files outside the main pipeline; the in-pipeline audit (3.1–3.3) re-derives the checks on the PPO population.
